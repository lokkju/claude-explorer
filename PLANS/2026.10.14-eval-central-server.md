# claude-explorer: central server evaluation

> Evaluation of a central multi-machine server for claude-explorer, written 2026-10-14.
> The direction chosen afterwards was to build on a fork of kenn-io/agentsview, [lokkju/agentsview](https://github.com/lokkju/agentsview), instead of extending claude-explorer.
>
> Correction: this report treats upstream rpeck/claude-explorer as a fork target that may be unmaintained. Upstream released v1.1.1, v1.1.2 and v1.1.3 on 2026-10-13.

Scope: aggregate conversations from several machines (laptop, the home server, pets, ephemeral agent jobs), several Claude accounts and several harnesses (Claude Code CLI, Desktop, Cowork, claude.ai web, possibly opencode) into one server, with search and browsing faceted by host, account/org, source, harness, project and model. Read-only evaluation of `/home/lokkju/projects/claude-explorer` at `1f5f08f`. Nothing in the repo was modified.

One framing fact first: `origin` is `lokkju/claude-explorer`, a fork of `rpeck/claude-explorer` (SECURITY.md:10 points disclosure at rpeck's repo). Upstream's premise is a single-user localhost tool, and most of what follows departs from that premise. Whether this lives as a fork-only feature or goes upstream as an opt-in mode is a decision to make before Phase 1, because it changes how much of the localhost behaviour has to survive untouched.

## 1. Current architecture facts that matter

### Source identity

- The source is a three-value literal, `Literal["CLAUDE_AI", "CLAUDE_CODE", "CLAUDE_COWORK"]`, duplicated on `ConversationListItem` (backend/models.py:134) and `ConversationSummary` (backend/models.py:188), and again in the `query()` and `search_conversations()` signatures (backend/search_index.py:1491, backend/search.py:274) and `_get_all_conversations_data` (backend/store.py:583). There is no host, harness, account or ingest-origin field anywhere. `CLAUDE_AI` covers both Desktop and claude.ai web, since both come from the same claude.ai API.
- The source tag is decided by *where the file was found*, not by its contents. `_enumerate_conversation_paths_with_roots` (backend/search_index.py:2414) tags each path by the root it came from, and the docstring calls that tag load-bearing because Cowork's `audit.jsonl` and CC's `<uuid>.jsonl` share an extension. A central server has to keep that property: a mirrored file must arrive with its source (and now its host) attached, not inferred.
- Org identity exists only for claude.ai data: `organization_id` / `organization_name` on the summary models (models.py:139-140, 205-206), stamped into each fetched JSON by the fetcher (fetcher/bulk_fetch.py:710-713) and laid out on disk as `by-org/<org>/<uuid>.json`. Cowork deliberately leaves `organization_id` unset even though its directory tree is `<deployment>/<org>/local_<uuid>/` (backend/cowork_reader.py:174-177, 221-228). Claude Code records no account at all.

### Identity data already present in the raw files

- Claude Code JSONL lines carry `sessionId`, `cwd`, `gitBranch`, `version`, `entrypoint` (`cli` observed; this is the field that separates CLI, SDK and Desktop-launched sessions), `userType`, and per-message `model`. The reader keeps `cwd` as `project_path`, `gitBranch`, `version` as `claude_code_version` (backend/claude_code_reader.py:256-262, backend/cc_message_transforms.py:676-695) and drops `entrypoint`.
- No hostname appears in CC JSONL. No account appears either; the only account identity is `~/.claude.json` `oauthAccount` (`accountUuid`, `emailAddress`, `organizationUuid`, `organizationName`), which describes the account logged in *now*, not the one that ran a given session. API-key sessions have none.
- Cowork lines carry `client_platform` (`desktop_app` in the fixture), the system-init `model` and `cwd`, and the sidecar JSON has `sessionId`, `model`, `cwd`, `isArchived`, `error` (backend/cowork_reader.py:116-173).
- The only `hostname` the codebase ever reads is in a migration log (fetcher/migrate_to_v2.py:201).

### Schema and index layout

- One SQLite file, `~/.claude-explorer/search-index.sqlite`, `SCHEMA_VERSION = 15` (backend/search_index.py:264). A version bump drops and rebuilds.
- `messages` is an FTS5 table (search_index.py:336-352) where everything except `title`, `body`, `body_text` is `UNINDEXED`: `conv_uuid`, `path`, `message_uuid`, `sender`, `created_at`, `source`, `project_path`, `organization_id`, the conv timestamps, `is_compaction_summary`. Filters on those columns are row scans over the MATCH result, not index lookups. Column ordinals are derived from `MESSAGES_COLUMNS` (search_index.py:317-332) because snippet() addresses columns by position; adding a column is mechanical but must go through that tuple.
- `conversations` (search_index.py:408-417) is a plain table, one row per `conv_uuid` (PK), with `title`, timestamps, `project_path`, `source`, `organization_id`. This is the right home for facet columns, because it can carry real B-tree indexes and is small (hundreds to thousands of rows against ~250K message rows).
- `indexed_files` (path PK, mtime, size, conv_uuid) and `conversation_summaries` (path PK, mtime, size, summary JSON) are keyed by **absolute on-disk path** (search_index.py:365-384). Drift detection is a stat walk over those paths.
- Search is scatter-gather: FTS5 returns `(conv_uuid, message_uuid)` and Python re-reads the matched conversations from disk to build snippets (CLAUDE.md "How search works"). The index is not the store. The detail view, exports and the linear-scan fallback all read the original files through `ConversationStore`. **A central server therefore needs the raw files (or an equivalent normalized store), not just index rows.**

### Paths, project_path and dedupe

- `project_path` is the raw `cwd` string from the originating machine. The same repo is `/home/lokkju/projects/infra` on the home server and something under `/Users/...` on a Mac, so group-by-project splits one repo into two projects once hosts are mixed. Cowork sets `project_path` to a VM sandbox path such as `/sessions/<vm>` (cowork_reader.py:136-152), which is per-session noise for project grouping.
- Multi-root discovery already exists. `Settings.claude_dirs` and `claude_desktop_app_dirs` are lists (backend/config.py:281-282) and the store and enumerator union across them with "primary wins" dedupe on session uuid (backend/store.py:557-579, 616-630; search_index.py:2465-2477). However the list is only ever `~/.claude` plus `$CLAUDE_CONFIG_DIR`, and an explicit `CLAUDE_DIR` or config override collapses it to a single path (config.py:189-222). There is no way to configure N labelled roots today.
- CC "continued" sessions spread one `sessionId` over two files; the store's Pass B (store.py:755-768) and the v15 `messages.path` column handle that. Desktop dedupes `by-org` against legacy flat copies (store.py:395-430).
- The missing-file pass deletes index rows for files that vanished, but only under roots it successfully walked (`readable_roots`, search_index.py:2441-2447, used by `_drift_first_scan` at 2594). That guard is what makes an rsync mirror safe to point at: a host whose mirror directory is absent does not lose its rows.

### Local filesystem assumptions

- CC images: message text contains `[Image: source: <abs-path>]` markers. `/api/cc-image?path=` serves only paths under the local `claude_dir/image-cache` (backend/routers/files.py:238-277), and exports gate on `image_marker_path_is_safe` against the same root (backend/exporters/_shared.py:80-95). On a central server every marker names a path on another machine. There is a permanent copy at `<data_dir>/cc-images/<conv-uuid>/...` (backend/cc_image_cache.py:10, 36-52), populated as a side effect of the origin machine reading the session, which a pet or agent job without claude-explorer installed never does.
- claude.ai attachments: cached bytes at `<data_dir>/../files/<conv>/<file>/<variant>.<ext>` (files.py:373-396), with a live proxy to claude.ai that loads the **single** credentials file `DEFAULT_CREDENTIALS_PATH` (files.py:55-81, fetcher/credentials.py:70). One credentials file holds one `sessionKey` with several orgs (fetcher/credentials.py:22-24, 130-135), so it is one account, not several.
- Bookmarks and preferences are single JSON files in `~/.claude-explorer/` keyed by conversation uuid (backend/routers/bookmarks.py:41-57).
- The watcher is watchdog (inotify) plus a 600s backstop poll (backend/cc_watcher.py:3-62, `scan_once` at 182), and it falls back to `PollingObserver` on NFS.

### Auth and security model

- There is none, by design. `serve` binds `127.0.0.1` by default (cli/main.py:356); CORS allows only the Vite dev origins (backend/main.py:934-940); no route checks identity. SECURITY.md is about disclosure channels and supply-chain audits; it has no threat model for network exposure. main.py:916-919 says outright that gzip on the event loop is acceptable "for a single-user localhost tool" and would need moving if the app became LAN-shared.
- Side-effecting routes are unauthenticated and several are `GET`: `/api/fetch/start` (backend/routers/fetch.py:545) and `/api/fetch/refresh` (fetch.py:1257), the latter launching an in-process Playwright login and writing credentials. On localhost that is tolerable. On a network it is CSRF bait: any page the operator visits could fire it.
- The corpus holds every conversation and every tool result, which includes pasted tokens, env dumps and `kubectl get secret` output. The credentials file holds a live claude.ai `sessionKey`.
- The MCP server is stdio only (mcp_server/server.py:688-689) and reads the local store; a central deployment needs it on HTTP behind the same auth.

## 2. Candidate architectures

### (a) Per-machine shipper pushing to a central ingest API

A small agent on each machine (systemd timer, launchd job, or a CC `SessionEnd`/`Stop` hook for agent jobs) sends either raw files or normalized conversation dicts to `POST /api/ingest`.

- **What to ship.** Raw files, not normalized records. The readers (`claude_code_reader`, `cowork_reader`, the Desktop JSON loader) are where most of this codebase's correctness work lives (prelude folding, compaction markers, continued-session merge, branch trees), and they change often. Shipping raw bytes lets the central server re-run new reader logic over old data, and keeps the shipper dumb enough to run in an agent container with only Python stdlib or curl. Normalized records would freeze today's reader output into the archive.
- **Data model.** The server writes each upload into a host-labelled mirror tree (`/data/hosts/<host>/claude/projects/...`, `/data/hosts/<host>/cowork/...`, `/data/accounts/<account>/conversations/by-org/...`) and the existing enumeration runs over those roots. Host is assigned by the server from the shipper's credential, never taken from the payload.
- **Incremental sync.** CC JSONL is append-only in practice. The shipper keeps `(path, size, mtime, sha256-of-last-4KB)` per file and sends `offset + bytes`; the server appends if its copy's size equals the offset and the tail hash matches, otherwise asks for the whole file. Cowork `audit.jsonl` is the same shape; its sidecar JSON and Desktop JSONs are whole-file replacements. Offline is natural: the laptop catches up on its next run; agent jobs ship once at exit and once from a `trap` on failure.
- **Retention.** Claude Code deletes JSONLs older than `cleanupPeriodDays` (the repo even ships scripts/check-cleanup-period.py). The server must never propagate deletions. The central server becomes the archive of record, which is a real gain over the per-machine setup.
- **Attachments.** The shipper sends `image-cache/` files referenced by the sessions it ships, and the server rewrites or resolves markers through a per-host image root. claude.ai attachments come from the fetcher (below), not the shipper.
- **Security.** Per-host bearer tokens, write-only: an ingest token can append to its own host's tree and nothing else, and cannot read. That matters most for agent job containers, which run untrusted code with whatever token they are given. Tokens live in SOPS Secrets for in-cluster jobs and pets, and in the OS keychain or a 0600 file on the laptop.
- **Cost.** A new ingest router, a shipper, token management, and the labelled-roots work that every option needs anyway.

### (b) Central server pulls (rsync over SSH, or syncthing-mirrored directories)

The server reads mirror directories that something else keeps current: `rsync -a` (no `--delete`) from a timer on each machine into the home server, or the server pulling over Tailscale SSH, or syncthing folders.

- **Data model.** Identical to (a) from the server's point of view: labelled mirror roots, host from the directory, not the payload.
- **Incremental sync.** rsync's delta transfer handles append-only JSONL well. Push-style rsync (client to server) tolerates the laptop sleeping; pull-style needs the target awake and reachable, which fails for the laptop and is impossible for ephemeral agent jobs (gone before the next pull). Syncthing is bidirectional by default, so a deletion on the laptop (CC cleanup) propagates to the mirror unless the server side is a receive-only folder with versioning; misconfigured, it deletes the archive.
- **Pets.** Pets on the home server are Incus containers whose rootfs sits on the home server's storage pool, so the server could in principle read `/var/lib/incus/storage-pools/.../rootfs/home/*/.claude` directly. That needs a privileged hostPath mount of another workload's filesystem. I would not do it; a push from inside the pet is cleaner.
- **Security.** Push-rsync needs an SSH account or rsync daemon on the receiving side, scoped per host with a forced command (`rrsync` restricted to `/data/hosts/<host>`). That gives the same write-only-per-host property as (a) with no new code on the server.
- **Cost.** Least new code. The weak point is agent jobs, which need a push at exit anyway.

### (c) Federation: local instances stay authoritative, central fans out queries

- **Data model.** No central copy. Each machine runs today's server (bound to its tailnet address with auth added) and the hub queries all of them.
- **Search.** BM25 scores from separate FTS5 indexes are not comparable (different corpus statistics), so merged ranking is approximate; the hub has to re-rank or sort by date. Facet counts need every node to answer.
- **Offline.** The laptop asleep means its history is invisible. Agent jobs and their transcripts disappear with the container, so federation cannot cover them at all. CC's own cleanup still deletes local history, so there is no archive.
- **Security.** Worst of the three: every machine exposes a read API over the whole corpus, and the most exposed machines (pets, job containers) become read endpoints.
- **Verdict.** Rejected. It loses the two things a central server is for (complete archive, offline machines searchable) and multiplies the attack surface.

### Desktop / claude.ai fetch

- The fetcher pulls from the claude.ai API with a `sessionKey` captured by an interactive Playwright login (fetcher/playwright_capture.py) and sends requests through `curl_cffi` to pass Cloudflare. One credentials file is one account with its orgs.
- Centrally, run one fetcher per account: `accounts/<name>/credentials.json` and `accounts/<name>/conversations/by-org/...`, driven by a CronJob or the server's existing scheduled-fetch code. Desktop and web are the same corpus per account, so a central fetch replaces every per-machine fetch and removes the duplicate copies that would otherwise arrive from two laptops logged into the same account.
- Login cannot happen in the cluster (no browser, no human). Capture on the laptop with the existing `claude-explorer capture`, then upload the `sessionKey` (the CLI already accepts `--session-key` / `--org-id`) into a per-account SOPS Secret or an authenticated admin endpoint. When the key expires the fetch reports `auth_expired` and the operator re-captures. the home server's egress is a residential IP, which is the same Cloudflare posture the laptop has today; I have not verified that `cf_clearance` captured on the laptop works from a different IP, and it may not.
- The attachment proxy (files.py:55-81) must look up credentials by org, not load the single default file.

### Dedupe when the same session appears from two places

- CC `sessionId` and Cowork `sessionId` are random v4 UUIDs, so the same uuid on two hosts means the same session copied (a synced `~/.claude`, a restored backup, a container image baked with a home dir), not a collision. claude.ai conversation uuids repeat legitimately across machines when two machines fetch the same account; central fetch removes that case.
- Global conversation key: `(source, uuid)` for CC and Cowork, `(source, org_id, uuid)` for claude.ai (the fetcher already treats `(org_id, uuid)` as the identity, fetcher/bulk_fetch.py:854-857). Keep `host` as a multi-valued attribute ("seen on"), and pick the canonical copy by largest size, then newest mtime, which is the right rule for append-only files. Today's rule is "primary root wins" (store.py:574-576), which is arbitrary once roots are hosts.

## 3. Faceting design

| Facet | Source of the value | Notes |
|---|---|---|
| `host` | Assigned by the server from the ingest credential or mirror directory | Never from payload. Pets and agent jobs need a naming convention (`pet:<name>`, `job:<repo>`) so agent jobs do not explode the facet into thousands of values; store the job id separately. |
| `source` | Existing enum | Keep. Extend only if a new harness needs a new reader (opencode). |
| `harness` | CC `entrypoint` (cli, sdk-*, desktop-launched), Cowork `client_platform`, `CLAUDE_AI` as `claude.ai` | Desktop vs web for claude.ai data is not distinguishable from anything the code reads today; I have not confirmed whether the API exposes a platform field. Treat claude.ai as one harness until shown otherwise. |
| `account` | claude.ai: the fetch account. CC: `~/.claude.json` `oauthAccount.accountUuid`/`emailAddress` captured by the shipper at ship time. Cowork: the `<org>` directory layer | CC attribution is approximate: it records the account logged in when the file was shipped, not when the session ran. A host that switches accounts mislabels sessions shipped after the switch. Shipping promptly (hook-driven) narrows the window. |
| `org` | `organization_id` (claude.ai, already indexed); Cowork `<org>` dir; CC `oauthAccount.organizationUuid` | Cowork's choice to leave `organization_id` unset (cowork_reader.py:174-177) would need revisiting. |
| `project` | `project_path` today | Normalize: a display key from the path basename, overridable by a server-side mapping (`/Users/x/src/infra` and `/home/lokkju/projects/infra` to `infra`). The shipper can add the git remote for the cwd, which is the reliable key when available. Exclude Cowork sandbox paths. |
| `model` | Per-message model in CC and Cowork; conversation `model` on claude.ai | Conversation-level facet from the dominant or last model; message-level filter is possible but rarely worth it. |
| `date` bucket | `conv_updated_at` | Already in both tables. |

Mapping onto the index:

- Add `host`, `harness`, `account_id`, `project_key`, `model` to the `conversations` table with B-tree indexes, plus a small `conversation_hosts(conv_uuid, host)` table for the multi-valued "seen on". Add `host` (and possibly `harness`) to `messages` as UNINDEXED only if per-message filtering is wanted; otherwise filter by joining the MATCH result's `conv_uuid` to `conversations`. Bump `SCHEMA_VERSION` to 16 and let the drop-and-rebuild path handle it.
- Facet counts are one query: `SELECT c.host, COUNT(DISTINCT m.conv_uuid) FROM messages m JOIN conversations c USING (conv_uuid) WHERE messages MATCH ? GROUP BY c.host`, repeated per dimension, or one query with `GROUPING SETS` emulated by `UNION ALL`. That is FUTURES.md S2's sketch (`/api/search/facets?q=` returning `by_source`, `by_project`), extended with the new dimensions. Browsing without a query uses the same GROUP BY over `conversations` alone.
- Filters should travel through the existing `conversation_uuids` TEMP-table mechanism (`_populate_allowed_conv`, search_index.py:2219-2246) or as new SQL predicates; the docstring at search_index.py:1510-1516 explains why a Python post-filter after top-N bm25 silently drops results, and that applies to every new facet.
- The sidebar already has source and workspace selects (UX.md:584-592). S2 was deferred for UX reasons (rail design, narrow viewport, keyboard); a central server makes it the primary navigation, so it stops being optional. The UX.md and test discipline in this repo (spec-first, count-verified Playwright) makes UI work slower than the backend work.

## 4. Deployment fit (k3s on the home server, Tailscale)

- One Deployment, one replica (SQLite, single writer), image built on the home server from a git commit and pushed to zot. Namespace labelled `tailnet-ingress` with an `ingressClassName: tailscale` Ingress, and added to `core/network-policies/namespace-labels.yaml` with explicit policies (Cilium `policyEnforcementMode: always`). Egress to claude.ai only if the central fetcher runs in this pod.
- Storage: the SQLite index on a `local-nvme` PVC, not NFS (WAL locking and the coarse-mtime issue noted at search_index.py:278-283). The raw mirror can live on local-nvme or TrueNAS NFS; NFS means the watcher falls back to polling, which the 600s backstop already covers. Back up the mirror at the highest criticality tier in STORAGE.md, since once CC cleanup runs on the origin machines it is the only copy.
- Auth: tailnet-only exposure is the outer wall. Inside it, use Tailscale identity (the operator's Ingress proxy can pass `Tailscale-User-Login` headers for tailnet users; verify with the installed operator version) or a simple session login, and an allow-list of one identity. Ingest tokens are separate, write-only and per host. Disable `/api/fetch/refresh`'s Playwright capture in server mode, and convert side-effecting GETs to POSTs with an origin check.
- Agent jobs run in namespace `agent-jobs` with `world-egress`-style policies; they reach the ingest endpoint over the in-cluster Service, which needs an explicit policy allowing that one port.

## 5. Effort, risks, recommendation

Estimates assume one person who knows this codebase's test discipline; the repo's spec-first rule and count-verified suites (CLAUDE.md "Test-execution integrity") roughly double raw coding time for anything touching the UI.

| Phase | Content | Effort |
|---|---|---|
| 1. Labelled roots + host facet, read-only server mode | Config accepts a list of `{host, claude_dir, desktop_app_dir, data_dir}` roots; host flows from root to conv dict, `ConversationSummary`, `conversations` table (schema 16); canonical-copy rule by size/mtime; host select in the sidebar beside source/workspace; `--server-mode` flag that disables fetch/capture/credential routes and writes; marker images resolved through the per-host `image-cache` root; rsync push (no `--delete`) from laptop and pets into the home server via `rrsync`; tailnet Ingress with Tailscale-identity check | 4 to 6 days |
| 2. Remaining facets + S2 rail | `harness` (keep `entrypoint`), `account`/`org` for CC and Cowork, `project_key` normalization with mapping file, `model`; `/api/search/facets`; facet rail UI per UX.md | 6 to 10 days, mostly UI and tests |
| 3. Ingest API + shipper | Append-offset protocol, per-host write-only tokens, shipper for laptop/pets, CC hook or job-exit step for agent jobs, image-cache shipping | 5 to 8 days |
| 4. Central multi-account fetch | Per-account credentials and data dirs, CronJob, sessionKey upload path, org-aware attachment proxy | 3 to 5 days |
| 5. HTTP MCP + other harnesses | MCP over streamable HTTP behind the same auth; opencode reader (storage format needs investigation; it has changed between versions) | 2 to 3 days for MCP; 3 to 5 days per new harness reader |

Risks:

- **Concentrated secrets.** The central store holds every transcript from every machine plus live claude.ai session keys. Encrypted-at-rest storage, tailnet-only exposure, one reader identity and write-only ingest tokens are the minimum; ingest-time secret redaction is worth considering but will miss things and should not be relied on.
- **Fork divergence.** Labelled roots, the host field and schema 16 touch store.py, search_index.py, models.py and the frontend list, which upstream changes constantly. Carrying this as a fork means rebasing over a moving schema (15 versions so far). Upstreaming an opt-in mode reduces that cost but has to pass upstream's localhost-first review.
- **CC account attribution is approximate**, as above.
- **Scale.** The linear-scan fallback (search.py dispatcher) walks every file when FTS is unavailable or still building. With several hosts and long retention that fallback gets slow; a first full index build at startup will take noticeably longer than on one machine.
- **Upstream format churn.** CC JSONL, Cowork's audit format and the unofficial claude.ai API all change without notice; raw shipping contains the damage to the readers, normalized shipping would not.
- **Syncthing deletion propagation** if (b) is done with syncthing instead of rsync.

**Recommendation.** Do (b) first, with push-rsync into labelled mirror roots on the home server, and move to (a) only for agent jobs and only when they need it. Phase 1 is the smallest useful step: labelled roots, a host facet, a read-only server mode with fetch and capture switched off, and tailnet-only exposure. It needs no ingest protocol, reuses the existing multi-root enumeration and the `readable_roots` safety guard, gives one place to search the laptop and every pet, and turns the home server into the archive that survives CC's cleanup. Keep fetching claude.ai on the laptop during Phase 1 and rsync its `~/.claude-explorer/conversations` up like any other root; central fetching (Phase 4) can wait until the multi-account question is real. Federation (c) should not be built.
