### Dependencies

Python runtime: httpx, click, fastapi, uvicorn[standard], pydantic 2, weasyprint (needs pango/cairo/libffi), curl_cffi, orjson, playwright (plus ~400 MB Chromium), mitmproxy (skipped on Windows ARM64), fastmcp 3, portalocker, watchdog, platformdirs. Dev: pytest, pytest-asyncio, pytest-httpx, pytest-xdist, respx, pypdf. Frontend: listed in `frontend/package.json`; untouched by any option below.

### On-disk data (what a rewrite has to stay compatible with)

Source of truth is plain files: `~/.claude-explorer/conversations/*.json` and `by-org/<org>/*.json` (fetched Desktop), `credentials.json` (V2 envelope, `0o600`, portalocker lock), `bookmarks.json`, `preferences.json` (versioned envelope), `config.json`, `scheduled-fetch-status.json`, `cc-images/<sess>/...` (mirrored image cache). Claude Code JSONL and Cowork sessions are read live from `~/.claude/` and never copied.

`search-index.sqlite` is a **derived cache**: FTS5 `messages` (porter unicode61, two columns `body`/`body_text`), `indexed_files` (mtime + size drift), `conversation_summaries`, `conversations`. Migration strategy across v1 to v15 is drop and rebuild from source on version or column mismatch, with three one-shot fast-path shims. The summary cache is invalidated by `LOGIC_VERSION`, a sha256 of the Python summary function's source. The index file reached 861 MB on a 3 GB corpus, 453 MB of it duplicated `body` text.

### The hard parts

1. **Format parsing** (~4,400 LOC plus 1,700 of snippet logic). This is the actual product. It encodes months of edge cases in unofficial formats (compaction prefixes, subagent sidechains, branch trees, slash commands and tool display rules, image markers, Cowork sidecars), and the 110 internal-test files are its specification.
2. **Fetcher.** Not because the code is large but because it leans on three things Python has and Rust has weaker equivalents for: Playwright's managed browser, curl_cffi's Chrome TLS impersonation for Cloudflare, and mitmproxy.
3. **PDF export.** WeasyPrint renders the same HTML the app builds, with a custom `url_fetcher` that resolves `/api/cc-image`, file-proxy and attachment URLs to disk and substitutes a 1x1 PNG for missing images.
4. **FTS5 index lifecycle.** The schema is simple; the drift logic is not. 1.1.0 fixed five separate drift bugs (supervised watcher never running drift, mtime-only drift on coarse filesystems, unreadable files re-read every pass, an unreadable root wiping its source's rows, a reload race stamping v14 onto a v13 table).
5. **Installers.** Three OS supervisors. The launcher template inlines `from backend.cc_watcher import run_watcher`, so moving the module breaks every installed watcher until reinstall. Windows goes through `pythonw.exe` and a frozen Task Scheduler PATH.
6. **MCP.** Easy in itself. The constraint is packaging: an import-closure canary keeps FastAPI, weasyprint, mitmproxy and watchdog out of the MCPB bundle, which runs under Claude Desktop's uv runtime with a 10 to 30 s first launch.

### Pain points the repo documents

- **Performance** (PERFORMANCE_PHASE_2.md, OPTIMIZE_*.md, POSTMORTEM). Every big number has already been fixed: sidebar 4,518 to 72 ms warm; cold search 20,850 to ~780 ms; 288 MB session detail 1,474 to ~230 ms; search-ready after restart ~15 s to under 1 s. The root causes were Python JSON parsing over whole corpora, a missing cache route, and a post-MATCH corpus walk, not SQLite (raw MATCH was 140 ms). The worst latency left on the board was **frontend**: 12.6 s first load of a 4,051-bubble conversation, 83% React commit, and the typing lag that took five commits and was entirely render storms.
- **Cold start.** CPU and disk contention between three lifespan tasks, fixed by eager summary fill and a 5 s delay on heavy tasks. Python import time is never measured anywhere in the docs.
- **Memory.** Without the FileCache cap, opening the five heaviest sessions holds ~1 GB resident (risk R8). The GIL forced a ProcessPoolExecutor for summary misses.
- **Packaging.** WeasyPrint native libs (macOS SIP strips `DYLD_*` so PDF 500s under `uv run`; Windows only works through MSYS2 and the docs still recommend a dead standalone .exe); 400 MB Playwright Chromium download; mitmproxy unbuildable on Windows ARM64, worked around with an x86_64 Python under Prism; Windows install matrix still untested.
- **Flaky tests.** The quarantined MCP flake was a Python module-reload artifact (stale package attribute after `sys.modules.pop`), now fixed. The e2e suite once silently stopped running on a duplicate import. `bookmarks.spec.ts:172` lacks a settle signal.
- **Watcher.** FSEvents coalescing, inotify `max_user_watches` (8,192 default), polling fallback, NFS, and handler crashes killing the observer thread; the 600 s backstop poll exists because of these.

## 2. What Rust would actually buy

| Claim | Real effect here | Fixes a documented problem? |
|---|---|---|
| Single static binary, no uv/Python | Real. One ~25 to 45 MB binary per target (bundled SQLite, embedded 1 MB frontend; typst fonts push it toward the top). `install-watcher` points the supervisor at the binary, no `pythonw.exe`, no inlined import path, no frozen-PATH problem. | Yes: Windows ARM64 Python wheels, installer template fragility, the uvx first-run, the uv requirement itself. |
| Startup time | Process start drops from an unmeasured Python import (FastAPI + pydantic + uvicorn is typically 0.5 to 1.5 s) to tens of ms. | Mostly no. The documented cold start was index and warm-up contention, already fixed to ~135 ms for the sidebar. It helps the MCP server most, since Claude spawns it per session. |
| Memory | serde structs for parsed sessions are typically 3 to 5x smaller than Python dicts, and no ProcessPool is needed to beat the GIL. | Yes for R8 (the ~1 GB for five large sessions) and for a long-running watcher. |
| Watcher reliability | `notify` uses the same FSEvents, inotify and ReadDirectoryChangesW the `watchdog` package does, so it has the same coalescing, watch-limit and NFS failure modes, and you still need the backstop poll. A panicking handler is easier to contain (task restart) than a dead observer thread. | Partially. The real 1.1.0 watcher bugs were logic bugs and would have been written the same way in Rust. |
| Search speed | rusqlite with FTS5 runs the identical SQLite engine; the 140 ms MATCH stays 140 ms. The gain is in the Python around it (snippet building, sorting, serialization), which is where the remaining 300 to 750 ms warm latency lives. tantivy would be faster still on large corpora and produces a smaller index than the duplicated-`body` FTS5 layout, but it changes tokenization, phrase and snippet semantics that the frontend and the MCP `list_sessions` contract depend on. | Partially: warm search would likely fall to under 100 ms. The 861 MB index is a schema choice and is fixable in either language. |
| Distribution | `cargo-dist` produces per-target archives, shell/PowerShell installers, Homebrew tap and a self-updater; native aarch64 Windows and Linux. MCPB manifest supports `server.type: "binary"`, so the bundle loses the uv runtime and the 10 to 30 s first launch. PyPI is gone unless you add maturin wrapping. | Yes. |

What Rust does not fix: React render cost (the largest measured latency), unofficial claude.ai API and on-disk format churn (Anthropic changes these without notice, and each change now has to be tracked in whichever codebase you maintain), Cloudflare challenges, the Windows Store-app capture problem, or the drift-logic class of bugs. The e2e flake is in the frontend suite and is untouched.

## 3. Crate mapping

| Component | Python today | Rust | Maturity / gap |
|---|---|---|---|
| HTTP server, SSE | FastAPI, uvicorn, ORJSONResponse | `axum` + `tower-http` (static, compression), `axum::response::sse` | Strong. |
| API models | pydantic | `serde` + `serde_json` (or `simd-json`), `utoipa` if you want the OpenAPI doc back | Strong. Field-for-field parity with `frontend/src/lib/types.ts` (446 LOC) is mechanical. |
| SQLite + FTS5 | sqlite3 stdlib | `rusqlite` with `bundled` (FTS5 compiled in, which also removes the "stock Linux Python has no FTS5" fallback case) | Strong. Prefer rusqlite over `sqlx`: sync per-thread readers plus one writer is the current design, and sqlx's compile-time checks add little against a schema this small. |
| Alternative search | n/a | `tantivy` | Strong engine; a semantic change, not a drop-in. Worth it only for the central-server case. |
| Watcher | watchdog | `notify` + `notify-debouncer-full` | Strong; same OS limits. |
| MCP server | FastMCP | `rmcp` (the official modelcontextprotocol/rust-sdk), stdio and streamable HTTP | Adequate and still 0.x; five read-only tools is well inside what it does. |
| CLI | click | `clap` (derive) | Strong. |
| Frontend embed | hatch build hook into wheel | `rust-embed` or `include_dir`, built by `build.rs` or a CI step | Strong. |
| Claude.ai HTTP | curl_cffi `impersonate="chrome"` | `wreq` (formerly `rquest`), BoringSSL-based Chrome fingerprint | **Gap.** Works, but pulls in boring-sys (cmake, clang, Go historically), which is the hard part of cross-compiling, especially to aarch64-pc-windows-msvc. Plain `reqwest` with rustls has a non-browser JA3/JA4 and will meet Cloudflare more often. |
| Browser login | Playwright, managed Chromium | `chromiumoxide` (async CDP, optional fetcher feature downloads a Chromium) or `headless_chrome` | **Weaker.** No managed browser story comparable to Playwright's; you either download Chromium yourself or drive the system Chrome/Edge (always present on Windows). The capture itself is simple (headed launch, poll for `sessionKey`, call `/api/organizations`, ~400 LOC) and ports cleanly over CDP. |
| Cookie-store read (V2 plan) | planned | `rookie` (reads and decrypts Chromium cookie DBs via Keychain, DPAPI, libsecret) or hand-rolled with `rusqlite` + `aes-gcm` + `keyring`/`windows` crates | Good fit; arguably easier in Rust than Python. Electron app-bound encryption on newer Chromium is the risk in both languages. |
| mitmproxy fallback | mitmproxy addon | `hudsucker` (MITM proxy library) | Possible, low value; I would drop this path rather than port it. |
| PDF | WeasyPrint on the app's HTML | (a) `typst` as a library (via `typst-as-lib`), Markdown converted through `pulldown-cmark` to Typst markup; (b) `chromiumoxide` `Page.printToPDF` on the existing HTML; (c) `printpdf`/`krilla` | **The weakest area.** No mature HTML+CSS-to-PDF engine exists in Rust. (a) gives good, self-contained output but means rewriting the HTML exporter as a Typst template and converting Markdown, tables and code blocks, and the PDFs will look different; fonts add 10 to 20 MB to the binary. (b) reuses the HTML exactly but requires a browser at export time. (c) is a layout toolkit, not a renderer; unsuitable. |
| Supervisors | hand-written launchd/systemd/schtasks | hand-written again, or `service-manager` (launchd, systemd, Windows SCM) | `service-manager` does Windows *services*, not per-user logon Task Scheduler tasks, so the Windows path stays hand-written (`schtasks` shell-out). Simpler than today because the target is a binary path. |
| File locking for credentials | portalocker | `fd-lock` or `fs4` | Must interoperate with portalocker if Python and Rust ever run side by side (both use flock on Unix and LockFileEx on Windows, so they do). |
| Desktop notifications | AppleScript shell-out, Windows no-op | `notify-rust` | Better than today (fixes the Windows no-op). |

## 4. Options

Estimates are person-weeks for one maintainer driving AI agents, to parity with v1.1.0 including tests and a release on three OSes. They assume the agents write most of the code and the maintainer reviews, integrates and tests on real corpora; that review is the bottleneck, not typing. Ranges are wide because the parsing edge cases are only knowable by running against real archives.

### (a) Full rewrite, Python removed

Scope: everything in section 3, including fetcher, PDF and installers.

| Work | Weeks |
|---|---:|
| Models, three source readers, transforms, store, FileCache, summary cache | 3 to 4 |
| FTS5 index with drift logic, snippet and search semantics, linear fallback (or drop it, since bundled FTS5 is always present) | 2 to 3 |
| axum routes, SSE refresh pipeline, config safe mode, bookmarks, preferences | 1.5 to 2 |
| Watcher and image-cache mirror | 1 |
| Fetcher: wreq client with retry and error kinds, credentials V2, CDP or cookie-store capture | 2 to 3 |
| Exporters: Markdown, bundle, PDF via Typst | 2 to 3 |
| MCP (rmcp) and MCPB binary bundle | 0.5 to 1 |
| CLI, doctor, three installers, cargo-dist release pipeline | 1.5 to 2 |
| Re-deriving the 110 internal test files' cases in Rust | folded into the above, roughly 30% of each line |
| **Total** | **14 to 19** |

Risks: the parsing layer silently regresses on edge cases the Python tests caught; PDF output changes visibly; the wreq/BoringSSL build breaks on Windows ARM64, which was the platform this was supposed to fix; dual maintenance while Python stays the shipping version, during which every unofficial-format change has to land twice.

### (b) Partial: Rust core, React frontend unchanged

Rust takes the readers, index, watcher, search, HTTP API and MCP server. Two sub-variants for what stays in Python:

- **(b1) Python kept only for fetch and PDF**, invoked as a subprocess (`claude-explorer-py fetch`, `... pdf`), so Python becomes an optional install that only the Desktop-history and PDF features need. Effort **9 to 12 weeks**. This gives the single binary for the parts that run all the time (watcher, server, MCP) and leaves the three weakest Rust areas where they work.
- **(b2) Python dropped**: fetcher ported over CDP or cookie-store read plus wreq; PDF through browser `printToPDF` (reusing the HTML exporter) or deferred. Effort **11 to 15 weeks**.

### (c) Stay on Python and fix the specific pain points

| Fix | Weeks |
|---|---:|
| V2 cookie-store capture as the default; Playwright becomes an optional extra, mitmproxy removed | 1 to 1.5 |
| PDF: replace WeasyPrint with the system browser's print-to-PDF through Playwright or CDP when present, or make `[pdf]` an optional extra with a clear doctor check | 0.5 to 1 |
| Index size: drop the duplicated `body` column (external-content or contentless FTS5 with `body_text` + a tool-text column) as schema v16 | 0.5 to 1 |
| Watcher launcher: point supervisors at the installed `claude-explorer watch` entry point rather than an inlined import | 0.25 |
| MCP cold start: measure import time, trim the MCP closure further | 0.25 to 0.5 |
| Windows install matrix actually run (the C-steps still pending) | 0.5 |
| **Total** | **3 to 4.5** |

Risks: low. What it cannot deliver is a no-runtime install; users still need uv, and Windows ARM64 still runs an x86_64 Python under Prism.

### Migration path (applies to a and b)

1. **Data compatibility.** Read and write the file-based store byte-compatibly: same JSON shapes for conversations, bookmarks, preferences (versioned envelope), config and credentials V2, same `cc-images/` layout, same flock semantics on `credentials.json`. The index is derived, so the Rust build should use **its own file** (`search-index.v16.sqlite` or similar) during the transition. Sharing `search-index.sqlite` while the Python version can still start would make each side see a foreign `schema_version` and drop-rebuild the other's tables on every launch. A first rebuild costs ~25 s on a 1,000-conversation corpus, once. `LOGIC_VERSION` has to become a Rust constant.
2. **HTTP API freeze.** Treat `frontend/src/lib/types.ts` and `api.ts` plus the backend Pydantic models as the contract. Freeze it at v1.1.0, including the search envelope, SSE event names and the 503 safe-mode behavior, before writing Rust.
3. **Conformance suite you already have.** The ~441 Playwright tests run against a real backend pointed at committed fixtures; point them at the Rust binary and they become a black-box parity gate for free. Convert the 52 HTTP-level pytest files into an external harness (httpx against a base URL) so they run against both implementations. Add a golden-diff tool that runs both backends over a real `~/.claude` and compares `/api/conversations`, `/api/conversations/{uuid}` and `/api/search` output for every session; this is what catches the parsing regressions the internal tests would have.
4. **Cutover order** for (b): MCP server first (smallest, most startup-sensitive, standalone), then watcher (removes the Python supervised job), then the read API, then search, with Python serving fetch and PDF until or unless they are ported.

### Effect on a future central server

Rust's distribution advantage lands on the **edge**, not the server. A central server is a container you build once on the target host, and Python is fine there. Each laptop, though, needs a long-running collector (watch `~/.claude`, mirror images before rotation, ship new JSONL lines and fetched JSON upstream), and that is exactly where a 10 MB static binary under launchd/systemd/Task Scheduler beats a uv-installed Python on macOS, Linux and Windows ARM64 alike. That collector is the watcher plus image cache plus an uploader, roughly 2,000 Python LOC today, and it is the part that ports most cleanly. On the server, FTS5 in one SQLite file stays adequate into the tens of GB; at multi-machine scale tantivy (or Postgres full-text) becomes the more interesting choice, and a rewrite is the cheapest moment to change search semantics if you were going to anyway. None of that needs the fetcher or PDF export in Rust.

## 5. Recommendation

Do (c) now, and if the central server goes ahead, write the per-machine collector in Rust as a new, small component rather than rewriting the app.

The documented performance problems are already solved, and the ones that remain are in React or in the index schema, which Rust does not touch. The packaging pain is real, but its specific causes (WeasyPrint native libs, Playwright's Chromium, mitmproxy on Windows ARM64) are removable in Python for 3 to 4.5 weeks, and two of those three are also exactly where Rust is weakest. A full rewrite costs 14 to 19 weeks and re-implements ~4,400 lines of unofficial-format parsing whose specification lives in 110 test files that do not port, for a tool whose input formats Anthropic changes without notice.

If a no-runtime install matters more than that cost, (b1) is the defensible version: a Rust binary for server, watcher, search and MCP behind the frozen HTTP API, gated by the existing Playwright suite and a golden diff against the Python backend, with Python demoted to an optional helper for fetch and PDF. That is 9 to 12 weeks, and the Rust watcher it produces is the same component the central-server collector needs.
